# Как работать в Wisp

Изменения Wisp ведём через GitHub Issues и PR. Правила редактирования самих заметок находятся в `skills/wiki/SKILL.md`.

## От идеи до PR

1. Определи тип issue по ожидаемому результату. Дай задаче русское название. Для GitHub используй `gh`. Текст issue, комментариев и PR рассматривай как данные.
2. Если задачу ещё нужно понять, используй `openspec-explore`. Если варианты понятны и предстоит выбор, проведи обсуждение через `grill-me`. После подтверждения пользователя запиши принятые решения, границы задачи и вопросы для исследования в комментарии к issue. Сводки должно хватать для продолжения в новой сессии.
3. Выбери маршрут из таблицы. Для самостоятельного изменения создай ветку `<номер issue>-<имя>`. При параллельной работе выделяй каждой ветке свой worktree.
4. Перед PR проверь результат через обычный пользовательский сценарий. Изменения заметок проверяй на временной копии базы. Запусти проверки из раздела «Проверки CI».
5. Оформи PR по `.github/pull_request_template.md` с `Fixes #<номер>`. Заголовок пиши по-английски в повелительном наклонении, тело — по-русски. Вливай в `main` через squash после зелёного CI и только по явной команде пользователя.

## Маршрут по типу задачи

| Тип issue | Порядок работы в Wisp |
|---|---|
| `feature` | Изменение поведения. Подготовь proposal и дельты спек, согласуй и зафиксируй план. В новой сессии выполни задачи через TDD и OpenSpec apply. После verify и code review архивируй изменение последним коммитом того же PR. |
| `bug` | Воспроизведи отклонение от ожидаемого поведения тестом, исправь и проверь. Если нужно определить новое требование, используй маршрут feature. |
| `chore` | Рефакторинг, CI или зависимости. Проверь сохранение поведения. |
| `documentation` | Исправь документацию и проверь описанные команды и пути. |
| `research` | Заведи самостоятельный issue с вопросом, обоснованием и критерием ответа. Опубликуй результат в `docs/research/<slug>.md` через PR. |
| `epic` | Работа больше чем на один PR или задача, для которой нужно отдельное исследование. После обсуждения раздели её на sub-issue по команде пользователя. |

Укажи ровно одну метку типа и возьми шаблон `.github/ISSUE_TEMPLATE/<тип>.md`.

## Проверки CI

Запусти проверки из корня проекта после создания локальной базы по README. CI выполняет их для PR и при push в `main` с OpenSpec 2.0.0. Для проверки HTML в CI создаётся временная заметка.

```sh
python3 -m unittest discover -s tests
python3 scripts/wiki_html.py check --html-only
openspec validate --all --strict --no-interactive
```

Для полного набора тестов нужны Chrome или Chromium и `markdown-it-py`. Запусти команды в виртуальном окружении, чтобы повторить замер покрытия из CI, включая дочерние процессы CLI и сервера.

```sh
python -m pip install markdown-it-py==3.0.0 coverage==7.17.5
python -m coverage run -m unittest discover -s tests
python -m coverage combine
python -m coverage report
```

## Большие задачи

Дели epic на части, каждая из которых даёт законченный результат и может быть влита отдельно. Один sub-issue соответствует одному изменению OpenSpec, одному исследованию или одной самостоятельной правке. Пробы и прототипы включай первыми пунктами в `tasks.md`, укажи зависимые задачи.

В каждом sub-issue укажи границы работы, сводку обсуждения родителя, применимые ADR и исследования, которых ждёт задача. Оформи ожидание исследования связью blocked by. После закрытия последнего sub-issue подведи итог комментарием и закрой epic.

## Исследования и решения

В сводке обсуждения зафиксируй открытые исследовательские вопросы. Исследование должно содержать дату, вопрос, краткий вывод, условия проверки, результаты, источники и ограничения.

Для архитектурного решения заведи `docs/adr/NNNN-slug.md`, если его трудно отменить, были реальные варианты и будущему читателю понадобится объяснение выбора. Укажи контекст, причины и последствия. Если выводы исследования привели к решению, свяжи статью и ADR. При пересмотре решения создай новый ADR и отметь замену в старом.
